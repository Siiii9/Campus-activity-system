### 1.3 协作流程
1. 创建 main 分支作为最终提交分支
2. 创建 dev 分支作为集成分支
3. 每人从 dev 创建自己的 feature 分支
4. 完成后通过 Pull Request 合并到 dev
5. 最终将 dev 合并到 main


## 2. WBS分解思路


### 2.1 分解原则
- 围绕交付物进行分解，不以"开会、讨论"等动作作为主线
- 至少分解到三级（L3），体现可管理的成果单元

### 2.2 三级分解逻辑
- **一级条目**：按成果域划分（如项目管理成果、系统功能说明成果）
- **二级条目**：按子成果划分（如项目基础文档、范围计划文档）
- **三级条目**：按具体交付物划分（如项目章程文件、WBS分解文档）

## 4. 配置管理过程


### 4.1 配置项识别
识别出的主要配置项包括：
| 配置项 | 文件名 | 责任人 |
|--------|--------|--------|
| 项目章程 | 01-project-charter.md | 全体 |
| WBS文档 | 02-wbs.md | zhangdongze |

| 总结报告 | 05-summary-report.md | 全体 |

### 4.2 分支策略
main # 最终提交分支（受保护）
└── dev # 开发集成分支
├── feature/config-plan # 配置管理分支
├── feature/plan # 计划分支（WBS+进度）
└── feature/conflict # 冲突演练分支

### 4.3 提交规范
格式：`<类型>: <描述>`
- docs：文档更新
- feat：新功能
- fix：问题修复
- chore：初始化/配置

### 4.4 合并规则
1. 所有功能分支从 dev 创建
2. 完成后向 dev 发起 Pull Request
3. PR 需至少1人审核
4. 由项目经理负责合并
5. 最终统一从 dev 合并到 main


## 5. 冲突解决过程

### 5.1 冲突制造过程

- 在 feature/conflict 分支编写 conflict.md 第一版
- sunbo 在其分支修改同一文件的同一位置
- 两人分别向 dev 发起合并，产生冲突


### 5.2 冲突解决方案

1. 拉取最新 dev 分支
2. 本地合并时 Git 提示冲突
3. 打开 conflict.md 手工编辑
4. 删除冲突标记（<<<<<<<, =======, >>>>>>>）
5. 保留双方合理内容
6. 重新提交
